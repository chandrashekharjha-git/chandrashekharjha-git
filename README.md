## Enterprise Architecture & Landing Zones

### Large-scale scenario

**Reference scenario:** migration of 100+ applications across Development, UAT and Production, spanning multiple Azure subscriptions, on-premises datacenters and cloud workloads.

The target platform should be scalable, robust, secure, reliable, portable, governed, highly available, backed up, monitored, compliant and cost optimised.

### Azure Cloud Adoption Framework (CAF)

I organise transformation around the CAF lifecycle:

- **Strategy:** business outcomes, drivers, risks, cost model and success measures
- **Plan:** application inventory, dependencies, skills, migration waves and roadmap
- **Ready:** landing zones, identity, connectivity, governance and operational foundations
- **Adopt:** migrate, modernise and validate workloads against agreed acceptance criteria
- **Govern:** policy, cost management, compliance, accountability and guardrails
- **Secure:** identity, network, compute, data and threat protection
- **Manage:** monitoring, service health, backup, incident response and continuous improvement

### Tenant and management-group design

- Design a clear management-group hierarchy, for example **Platform**, **Landing Zones**, **Sandbox** and **Decommissioned** branches, adapted to enterprise requirements.
- Separate platform subscriptions from application/workload subscriptions.
- Define subscription onboarding and offboarding standards, ownership, naming, tagging and lifecycle controls.
- Assign Azure Policy definitions and initiatives at the appropriate management-group or subscription scope.
- Use policy exemptions sparingly, with documented justification, owner, expiry/review date and compensating controls.
- Apply Microsoft Entra ID groups and role-based access control (RBAC) using least privilege and separation of duties.
- Keep emergency access, privileged administration and workload identities under explicit governance.

> Design principle: keep the hierarchy understandable, delegate responsibility deliberately, and apply controls at the highest scope that matches the requirement without creating unnecessary exceptions.

## Hub-and-Spoke Networking

- Establish IP address management (IPAM) and CIDR planning before provisioning.
- Assess on-premises CIDRs, overlapping ranges, routing requirements and future growth.
- Design a central hub for shared connectivity and inspection, with workload spokes segmented by application, environment or risk.
- Use VNet peering with deliberate routing and security boundaries.
- Apply user-defined routes (UDRs) to direct required traffic through Azure Firewall or approved network virtual appliances.
- Configure firewall rules and controlled outbound egress according to documented application flows.
- Use Private Endpoints and Private DNS zones for supported PaaS services where private access is required.
- Design site-to-site VPN and/or ExpressRoute connectivity based on throughput, resiliency, latency and business requirements.
- Validate DNS resolution, effective routes, network security rules, failover and on-premises reachability.

## Terraform & DevSecOps Engineering

### Terraform practices

- Build reusable, versioned modules with clear inputs, outputs and documented contracts.
- Use `for_each` and maps for repeatable resource creation when it improves clarity and lifecycle stability.
- Separate reusable modules from environment-specific root configurations.
- Use remote state with restricted access, encryption at rest, state locking where supported, and recovery controls.
- Separate state by environment and workload boundary; use dedicated storage containers or accounts according to isolation requirements.
- Store secrets in Azure Key Vault or an approved secret-management service; do not hardcode secrets in Terraform files or variable files.
- Pin Terraform and provider versions deliberately; commit `.terraform.lock.hcl` to record provider selections.
- Exclude generated state and local working directories from Git: **do not commit `terraform.tfstate`, state backups or `.terraform/`**.
- Run formatting, validation, linting, security scanning, testing and cost estimation before approval.
- Use least-privilege identities for planning, deployment and state access.
- Detect drift through scheduled or event-driven CI/CD plans, then review and remediate drift through controlled change management.

### Example secure pipeline stages

1. **Pre-commit:** formatting, basic validation and secret checks
2. **Pull request:** linting, Terraform validation, unit/module tests and IaC scanning
3. **Plan:** authenticate with workload federation/OIDC where supported, initialise backend and publish plan output
4. **Review:** policy/compliance checks, cost review and mandatory approval
5. **Apply:** controlled deployment using an approved plan and least-privilege identity
6. **Post-deployment:** smoke tests, policy verification, monitoring checks and evidence capture
7. **Drift management:** scheduled plan, alert, triage and controlled remediation

Potential tools, where adopted: **Checkov, Trivy, TFLint, tfsec, Gitleaks, Infracost, Azure Policy and Defender for Cloud**.

## Large-Scale Cloud Migration

### Migration lifecycle

1. **Discover:** inventory applications, infrastructure, owners, interfaces, data flows and dependencies.
2. **Assess:** evaluate business criticality, technical fit, licensing, compliance, latency and migration complexity.
3. **Plan:** define migration strategy, waves, landing-zone dependencies, downtime windows, rollback and communications.
4. **Prepare:** validate connectivity, identity, access, DNS, backup, monitoring, security and target capacity.
5. **Migrate:** execute the agreed approach — rehost, replatform, refactor, replace, retire or retain — based on workload needs.
6. **Cut over:** follow a time-bound runbook with named owners, checkpoints, go/no-go criteria and rollback triggers.
7. **Validate:** test application functions, integrations, data integrity, performance, security and business acceptance.
8. **Hypercare:** monitor incidents, performance, cost and user feedback; close issues and transfer to operations.
9. **Optimise:** rightsize resources, remove obsolete infrastructure and update architecture/documentation.

- Keep Development, UAT and Production appropriately isolated through subscription, network, identity and policy design.
- Use repeatable deployment pipelines and environment-specific configuration.
- Define pre-migration, cutover, post-migration and rollback checklists.
- Track application dependencies and migration readiness in a central wave plan.
- Obtain application-owner and business sign-off before closing a migration wave.

## Application & Kubernetes Platform Engineering

### Containerisation strategy

- Package applications into reproducible container images.
- Use multi-stage Docker builds to keep runtime images lean.
- Pin base images to approved versions and update them through controlled pull requests.
- Run containers as non-root wherever supported.
- Keep secrets out of Dockerfiles, build arguments and image layers.
- Add health checks and sensible resource limits.
- Use `.dockerignore` to reduce build context and avoid copying local files.
- Scan images before publishing them to a registry.
- Tag images with immutable commit identifiers in addition to human-readable release tags.
- Generate a software bill of materials (SBOM) when required by the security process.
- Sign and verify images where the platform and release process support it.
- Promote the same tested artifact through Dev, UAT and Production rather than rebuilding it for each environment.
- Define image retention and cleanup policies for registries.
- Document container build inputs, outputs, dependencies and supported architectures.

### Kubernetes and AKS design

- Separate application namespaces by environment, team or trust boundary according to the platform model.
- Use Kubernetes RBAC and Azure identity integration to restrict access.
- Define CPU and memory requests and limits based on measured workload behaviour.
- Apply pod security standards and restrict privileged containers.
- Use NetworkPolicies where supported by the selected networking configuration.
- Configure liveness, readiness and startup probes appropriately.
- Use PodDisruptionBudgets for workloads that require availability during voluntary disruptions.
- Spread replicas across nodes and zones when supported and required by the workload.
- Use topology spread constraints or pod anti-affinity where appropriate.
- Configure HPA for workload-level scaling and cluster autoscaler for node capacity.
- Evaluate VPA recommendations and adoption carefully alongside HPA and application behaviour.
- Use dedicated node pools for system workloads or specialised application requirements when justified.
- Define maintenance windows and upgrade procedures for Kubernetes and node images.
- Test Kubernetes version upgrades against application compatibility and add-on support.
- Set resource quotas and limit ranges to prevent noisy-neighbour issues.
- Use admission controls and policy enforcement for baseline configuration.
- Manage cluster add-ons and extensions through a controlled lifecycle.
- Define backup and recovery expectations for cluster configuration and persistent data.
- Document operational procedures for node pressure, pending pods, image pull failures and scheduling errors.

### Helm chart engineering

- Use Helm charts to package repeatable Kubernetes application deployments.
- Separate chart templates from environment-specific values.
- Keep default `values.yaml` safe and suitable for local development.
- Use additional values files for Dev, UAT and Production differences.
- Avoid placing passwords, tokens or certificates directly in values files.
- Validate charts with `helm lint` before merging.
- Render templates with `helm template` during CI validation.
- Test rendered manifests with schema, policy and security checks.
- Use chart versioning and application versioning deliberately.
- Document configurable values, defaults and required parameters.
- Prefer explicit values over deeply nested implicit defaults.
- Keep templates readable and avoid overusing complex template logic.
- Use named templates for shared labels, selectors and repeated structures.
- Follow Kubernetes label conventions and stable selectors.
- Define resource requests, limits, probes and security context in chart defaults.
- Provide examples for ingress, service, deployment and autoscaling configuration where relevant.
- Use dependency declarations carefully and pin dependency versions.
- Package and publish charts to an approved OCI-compatible registry or chart repository.
- Review chart changes through pull requests and preserve release notes.
- Use `helm upgrade --install` in controlled deployment workflows where appropriate.
- Use `helm diff` or equivalent review mechanisms when available before applying changes.
- Define rollback criteria and understand the limitations of Helm rollback for database or external-system changes.
- Test chart upgrades and rollback scenarios in non-production before production rollout.
- Avoid relying on manually changed cluster resources that are not represented in chart values or source control.
- Record the chart version and image digest used for each release.

### Argo CD and GitOps

- Use Git as the declarative source of truth for Kubernetes application configuration.
- Adopt Argo CD to continuously reconcile the cluster state with the desired state in Git.
- Separate application source, Helm chart source and environment configuration according to team ownership and release needs.
- Use Argo CD Applications or ApplicationSets to manage repeatable application deployment patterns.
- Design AppProjects to restrict permitted repositories, destinations and resource kinds.
- Apply least privilege to Argo CD service accounts, repository credentials and cluster access.
- Store repository credentials and deployment secrets through approved secret-management integrations.
- Avoid storing plain-text secrets in Git; evaluate External Secrets Operator, CSI integrations or a platform-approved secrets workflow.
- Choose automated sync, prune and self-heal settings based on workload risk and operational controls.
- Require review and promotion controls for production Git changes.
- Use sync waves or hooks only when ordering is genuinely required and the behaviour is understood.
- Configure health checks and application status reporting to help teams identify degraded deployments.
- Use ApplicationSets for standardised multi-cluster or multi-environment deployment patterns where appropriate.
- Separate platform-level and application-level GitOps responsibilities.
- Keep cluster bootstrap and Argo CD installation procedures documented and recoverable.
- Define repository layout conventions for applications, charts and environment overlays.
- Use pull requests to promote configuration from Dev to UAT and Production.
- Preserve a clear audit trail of who changed desired state, what changed and which commit was deployed.
- Monitor reconciliation failures, drift, sync errors and degraded application health.
- Define an operational process for manual emergency changes and reconciliation back to Git.
- Document how to pause automated sync safely during an incident and how to restore normal reconciliation.
- Test disaster recovery for Git repositories, Argo CD configuration and required credentials.
- Avoid allowing broad production write permissions to every application team.
- Review Argo CD version, extensions and API compatibility during upgrades.

### CI/CD versus GitOps responsibilities

| Capability | CI pipeline | GitOps / Argo CD |
|---|---|---|
| Source checks | Validate and test application source | Validate desired-state configuration |
| Build | Build application artifact or image | Normally does not build application images |
| Security | Scan dependencies, source, IaC and image | Enforce or report deployment-time policy |
| Publish | Push immutable images and chart packages | Retrieve approved configuration and artifacts |
| Promotion | Update environment configuration through reviewed change | Reconcile approved Git state to the cluster |
| Deployment status | Publish build and release evidence | Report sync, health and reconciliation state |
| Rollback | Revert artifact or release inputs when appropriate | Revert desired state in Git and reconcile |
| Audit | Record build provenance and test results | Record Git change and deployed desired state |

A common pattern is: CI builds and scans the image, publishes it with an immutable digest, then opens a reviewed pull request to update the Helm values or deployment manifest. Argo CD reconciles the approved change to the target cluster.

### Kubernetes troubleshooting checklist

- Check pod status, events, logs and previous container logs.
- Confirm image name, tag or digest and registry access.
- Verify resource requests, limits, quota and node capacity.
- Inspect readiness, liveness and startup probe failures.
- Check service selectors, endpoints and ingress configuration.
- Validate DNS, NetworkPolicy, routes, firewall rules and private endpoint dependencies.
- Review HPA metrics availability and autoscaler events.
- Inspect PVC binding, storage class and mount events.
- Check workload identity, Kubernetes RBAC and external secret access.
- For Helm, inspect release status, rendered manifests and chart values.
- For Argo CD, inspect application sync status, health status, repository access and comparison results.
- Prefer evidence-driven diagnosis over repeated restarts.
- Record root cause, remediation and preventive actions after incidents.

## Application Migration Governance: 100+ Workloads

- Map upstream and downstream dependencies before assigning a migration wave.
- Classify applications by complexity, risk, downtime tolerance and target architecture.
- Group migrations by dependency, business calendar and platform readiness.
- Define wave entry criteria, exit criteria and approval gates.
- Track blockers, assumptions, risks, issues and decisions in a shared register.

### Pre-migration checklist

- Confirm approved architecture and landing-zone readiness.
- Confirm connectivity and name resolution between source and target.
- Validate identity, access, service accounts and secrets handling.
- Confirm backup coverage and successful restore evidence.
- Validate target capacity, quotas, IP allocation and service availability.
- Capture baseline performance and application health.
- Verify monitoring, alert routing and operational ownership.
- Confirm migration tools, access permissions and execution steps.
- Review data synchronisation, consistency and downtime requirements.
- Approve cutover window, go/no-go criteria and rollback plan.

### Cutover checklist

- Confirm change approval and stakeholder availability.
- Verify the source system is in the expected state.

## Architecture Decision Records (ADRs)

For significant architecture decisions, record:

- **Context:** the problem, business need and constraints.
- **Decision:** the chosen option and its scope.
- **Alternatives:** credible alternatives considered.
- **Consequences:** trade-offs, costs, operational impact and risks.
- **Security:** identity, network, data and compliance implications.
- **Resilience:** availability, backup, recovery and failure-mode implications.
- **Ownership:** decision owner, reviewers and date.
- **Review trigger:** events or conditions that would justify revisiting the decision.

Example ADR topics:

- Management-group and subscription boundaries
- Hub-and-spoke versus alternative network topologies
- Private Endpoints and DNS ownership
- Terraform state isolation
- Azure DevOps versus GitHub Actions for a given workload
- Helm-based release management and Argo CD GitOps adoption
- Regional disaster-recovery strategy
- Log retention and cost controls

## Practical Git & Repository Standards

- Use meaningful branch names such as `feature/landing-zone-policy` or `fix/helm-probe`.
- Keep branches short-lived and regularly synchronised with the target branch.
- Write commits that describe the change and its intent.
- Keep pull requests focused and include test evidence.
- Use a pull-request template to capture purpose, risk, testing and rollback.
- Add CODEOWNERS or equivalent review ownership for sensitive directories.
- Protect default branches from force-push and accidental deletion.
- Require build validation for important repositories.
- Keep generated files and secrets out of source control.
- Use `.gitignore` for Terraform state, local caches and other generated artifacts.
- Do not Commit `.terraform.lock.hcl` for Terraform provider reproducibility.
- Use release tags and changelogs for versioned modules or charts.
- Avoid storing production state files or confidential environment data in repositories.
- Document repository purpose, maintainers, support model and contribution process.
- Archive or decommission repositories through an approved lifecycle process.
